## 1. 电梯陈述

### 30 秒版

> 我做了一个中文外卖评论的情感分析平台，分两条轨。Track A 是字符 n-gram TF-IDF 加词典特征加逻辑回归，本机 19 秒能训练完，test macro-F1 0.8949，进 FastAPI 服务，每条预测能给特征贡献解释。Track B 是 LoRA 微调链路，量化出微调的边际收益。

### 90 秒版（完整）

> 起点是一个很朴素的工程问题：我想知道一个情感分类模型在自己的机器上、自己的数据上，真实指标是多少，而不是抄论文里的数字。
>
> 我的机器是 Apple Silicon 没有独立 GPU，所以我拆成了两轨。Track A 零重依赖，19 秒跑完，每条预测能解释"是哪些字推动了这个结论"，这是它进 API 的理由。Track B 是 LoRA 微调，跑 5 分钟，用来量化一件事——**微调到底值不值**。
>
> 结论有点反直觉：现成的零样本专用模型 macro-F1 0.9689，比我自己微调的 LoRA 0.8983 高 7 个点。而 LoRA 相对 Track A 只提升了 0.34 个点，**置信区间高度重叠，统计上就是噪声**。
>
> 我没回避这个结果，反而把它写成了 README 的核心章节：**知道什么时候不该用更贵的方案**。真正有价值的是那个"零样本先建基线"的决策规则，和量化出来的边界在哪。
>
> 工程上我比较在意纪律：超参只在 dev 上选，test 只评估一次并写进 JSON 被 CI 断言，两轨共用同一份划分，数据先去重去冲突再分层切，指标只有一份实现，报 bootstrap 置信区间而不是裸数字。

## 4. Q&A 主体

### A 组 · 项目总体与设计取舍

---

**A1. 为什么要拆成两轨？直接用一个不行吗？**

一句话：这台机器没有独立 GPU，单一方案会同时丢掉"可复现"和"能微调"其中之一。

- 只有 LoRA → 别人 clone 下来装 torch 要几分钟到十几分钟，CI 也拖垮；
- 只有朴素模型 → 撑不起"LLM 微调管线"这条线，项目天花板太低。

拆开之后，**Track A 只依赖 numpy/sklearn/scipy**，CI 一分钟内能跑完全部测试；Track B 的测试用 `requires_torch` 标记自动 skip。CI 里还有一步是**主动断言 torch 真的没装**——防止有人顺手把 torch 加进 requirements，拖慢流水线。

**追问：CI 怎么保证 Track B 的代码不会悄悄坏掉？**
诚实答：保证不了完全覆盖。CI 只验证 Track A 完整链路 + Track B 的纯逻辑（指标复用、配置解析）。Track B 的真实训练只在本地跑过，CI 每次跑 5 分钟训练不现实。这是取舍。

---

**A2. 你为什么说是"平台"而不是"一个 demo"？**

一句话：它的价值在**接口契约和产物落盘**，不在模型。

- 7 个 REST 端点，有 Pydantic 契约（`app/schemas.py`）；
- `GET /api/metrics` **不在运行时重算**，直接透传磁盘上的 `reports/*.json`，保证线上看到的和训练产出严格一致；
- 模型产物 joblib 不入库，由 smoke test 自动重训——因为 joblib 与 sklearn 版本强相关，入库必炸。

**追问：为什么不把 joblib 入库？**
因为 joblib 文件格式与 pickle 协议、sklearn 版本强绑定。入库的模型在别人机器上大概率 `InconsistentVersionError`。我的做法是捕获这个异常转成可读错误，同时不把产物入库，改由 CI 真实训练一次。代价是 clone 后要跑 19 秒。

---

### B 组 · 数据工程

---

**B1. 你说发现了数据泄漏，具体是什么？怎么发现的？**

一句话：11,987 行里有 **7 条文本被标了相反标签 + 5 行完全重复**，按行随机划分会让同一条文本同时出现在 train 和 test。

发现方式是清洗阶段主动审计，不是事后看指标觉得"好得可疑"。处理顺序是**先去重、再丢冲突、最后才分层划分**：

1. 按**归一化后**的文本去重（`normalize` 会统一全角/半角，所以"同等"文本能合并）；
2. 同一条文本出现不同标签 → 无法判断哪个对，**整条丢弃**（不是投票多数）；
3. 剩 11,968 条，再按标签分层打散划分。

**追问：为什么用归一化文本做 key，而不是原始文本？**
因为归一化后去重更激进，能合并肉眼看着不一样但实际等价的样本。反过来说，这也埋了一个坑，见 B4。

---

**B2. 为什么自己实现 LCG，不用 `random` 或 `numpy`？**

一句话：我要的是**跨 Python 版本逐位可复现的划分**，不是为了随机数质量。

```python
self.state = (1664525 * self.state + 1013904223) & 0xFFFFFFFF
```

**这里我要主动补一句承认**：LCG 的低位周期很短，严格说随机性不如 PCG64 或 Mersenne Twister。如果只要"本机可复现"，直接用 `np.random.default_rng(seed)` 就够了（numpy 对 `default_rng` 有 stream compatibility 承诺）。我选自实现是因为 `random.shuffle` 的**算法实现没有版本兼容承诺**，跨 Python 版本可能变。LCG 只有 4 行、无依赖、行为完全可控。

**追问：那这个划分的随机性够吗？**
对分层划分够用，因为我的用法是 Fisher-Yates 洗牌 + 每组内部切分，不依赖低位比特的统计性质。但如果要做多次重复实验取分布，LCG 不够，得换 PCG64。诚实边界。

---

**B3. 为什么用分层划分？类不均衡具体怎么处理？**

数据是负面 7,978 / 正面 3,990，约 2:1。三个层面处理：

1. **划分**：按标签分组，组内独立洗牌，保证三个子集比例一致（train 6,382/3,192，dev/test 各 798/399）；
2. **指标**：主指标 macro-F1，对两类等权；
3. **训练**：提供 `class_weight='balanced'`，由 dev 实测决定——结果确实更好，被选进最优配置。

**追问：accuracy 为什么不行？**
这是本项目最好的教学点。全预测多数类的 baseline accuracy 高达 **0.6664**，看起来"还行"，但 macro-F1 只有 **0.3999**——因为正面类召回是 0。业务上，一个把所有评论都判负面的模型毫无价值。CI 里有一条断言专门守这个：模型 macro-F1 必须显著优于 dummy。

---

**B4. 讲一个你踩过最典型的坑。**

**两轨划分对不上。** 修改 `normalize` 的逻辑后，去重结果变了，Track A 的 test 变成 1,197 条，Track B 却还是 1,196 条——同一份数据，切出来不一样。

根因链条：`normalize` 改变 → 去重 key 改变 → 清洗后样本数改变 → 分层划分的结果改变。

修法：**重跑 Track B**，并在 README 里明确写死"两轨共用同一份划分（同一个 seed、同一份 `dataset.py`）"。

**这个坑想说明什么？** 跨轨对比的前提是同一份划分，否则"谁更强"这个问题根本不成立。这也是我坚持把划分逻辑收敛到唯一一个模块、不允许两边各写一套的原因。

---

**B5. 为什么用字符 n-gram，不用 jieba 分词？**

一句话：外卖评论是**短文本 + 错别字多 + 领域外**，分词器切错代价很高，而字符 n-gram 天然规避。

三个理由：

1. **不依赖词典和分词器**，训练/推理链路零额外模型依赖，便于跨环境复现；
2. **对未登录词、错别字、方言鲁棒**——外卖评论里这三样都很常见；
3. **否定关系天然落在 2~4 gram 上**：`"不好吃"` 和 `"很好吃"` 的差异直接体现为不同的 n-gram，不需要显式写否定规则。

代价我也认：特征维度更高。实测特征 61,968 维，而训练样本只有 9,574 条，**约 6.5 维/样本**，这是相当高的维数比，所以 `min_df=2` 剪掉只出现一次的单字 n-gram。

**追问：那词典规则不是显式处理否定吗？和 n-gram 重复吗？**
不重复，是两条独立路径。n-gram 负责泛化，词典负责**可解释性**。见 C5。

### C 组 · Track A 与评估方法学

---

**C1. 为什么选逻辑回归，不上 SVM / 随机森林 / XGBoost？**

一句话：因为我要**每条预测都能给出特征贡献解释**，线性模型是唯一能把这个解释做得数学上干净的选择。

特征是 61,968 维稀疏的，逻辑回归在这种高维稀疏数据上本身就是很强的 baseline，而且：

- 训练 19 秒（含 18 组网格搜索），可复现；
- 系数直接可读；
- `solver='liblinear'`，二分类 + 小样本的经典选择，支持 `class_weight`。

**追问：你试过树模型吗？**
没有，这是我明确的边界（见 §6）。诚实说：我知道在这个特征上 GBDT 大概率还能再涨 1–2 个点，但我优先保证了可解释性和复现速度。如果目标是纯精度，我会先跑树模型。

---

**C2. 消融结果里，去掉稠密词典特征只掉 0.001 个点——那这 22 维不是白加的？**

一句话：**精度上确实是白加的，但它的价值不在精度，在可解释性**。我不打算把它包装成"显著提升"。

消融实测：

| 变体 | dev macro-F1 |
| --- | --- |
| 完整模型 | 0.8780 |
| 去掉稠密词典特征 | 0.8770 |
| n-gram 改 1–3 | 0.8770 |

诚实的解读是：**在这份数据上字符 n-gram 是绝对主力**，词典特征只值 0.001。但我保留它，因为它给 `/api/predict` 提供了人话解释——用户看到的不只是"负面 0.87"，而是"命中负面词『难吃』『凉』，且『没』构成否定翻转"。

这是一个**用精度换可解释性**的自觉取舍，不是失误。README 里原话就是"我不想把它包装成'显著提升'"。

---

**C3. 你怎么保证 test 集只被评估一次？**

一句话：这不是靠自觉，是**写进产物 + CI 断言**。

- `trainer.py` 里 test 只出现在一处：`train_and_evaluate` 的第 237–244 行，注释就写着 `↓↓↓ test 集唯一一次被使用 ↓↓↓`；
- 网格搜索、基线、消融**全部只看 dev**；
- `"test_evaluations": 1` 写进 `reports/evaluation.json`，README 明确引用这个字段；
- Track B 同样：逐 epoch 在 dev 上选优，保留最优权重，最后只评一次 test。

**追问：dev 也被反复用了十几遍，dev 不也算"污染"了吗？**
算，而且这是真实的局限。dev 只有 1,197 条，macro-F1 本身的抽样噪声就有几个百分点，18 组网格里选出的"最优"可能有相当一部分是噪声。更严谨的做法是 repeated CV 或 nested CV，我没做，因为要保持 CI 一分钟内可复现。这是明确的取舍。

---

**C4. 为什么报 bootstrap 置信区间？200 次够吗？**

一句话：报区间比报裸数字诚实，但 **200 次确实偏少，我认这个局限**。

做法是百分位法 bootstrap：每次有放回重采样 1,197 条，重算 macro-F1，重复 200 次，取 2.5% 和 97.5% 分位点。

**为什么给区间？** 因为 Track A 和 Track B 差 **0.34 个点**，而两个区间分别是 `[0.8760, 0.9135]` 和 `[0.8809, 0.9158]`——**几乎完全重叠**。所以我不能说"LoRA 提升了 0.34 个点"，我只能说"两者在统计上不可区分"。

**200 次够不够？** 不够严谨。百分位法在 B=200 时，2.5% 分位点实际上只由第 5 个有序统计量决定，估计噪声不小。正式报告我会提到 1000–10000 次，README 里写 200 是为了控制耗时。**这是我明说的边界。**

**追问：更正确的比较方法是什么？**
两个模型在**同一个 test 集**上，应该用 **McNemar 检验**（配对二分类显著性检验），而不是比两个独立置信区间。McNemar 只看两模型判断不一致的那部分样本，配对效率更高。我应该补这个检验——这是我知道该做但还没做的。

**追问：bootstrap 能说明什么，不能说明什么？**
它衡量的是**给定这个模型**时的抽样不确定性。它**不包含**超参选择带来的不确定性——dev 上选参数这件事本身是第二步，bootstrap 只覆盖第一步。严格的说法应该是"条件于已选定的模型"。

---

**C5. 线性模型怎么给可解释性？为什么贡献度可以直接解读？**

一句话：单特征贡献 = `权重 × 该样本的特征取值`，**在二分类下这个量可以直接解读成 logit 差值的增量**。

推导：逻辑回归二分类的决策是 `w·x + b`。softmax 两项的分母 `e^a + e^b` 对两项是**公共因子**，所以比较两类只取决于 logit 差值。第 i 个特征对差值的贡献就是 `coef[i] * x[i]`。这是精确的，不是近似。

实现（`app/models/service.py:_explain`）：

```python
x = pipeline.transform([text]).toarray()[0]
coef = classifier.coef_[0]           # 二分类下 shape = (n_features,)
contributions = x * coef
```

然后按符号拆成 `top_positive` / `top_negative` 两组，各自按绝对值排序。

另外还叠了一层"人话解释"：把词典命中里**与模型结论同向**的那些挑出来（`aligned`），所以用户看到的是"命中负面词『难吃』，且被『没』否定翻转"，而不是一堆看不懂的 n-gram。

**追问：61,968 维里绝大多数是 0，这个解释会不会被大量零特征淹没？**
会。代码里直接过滤 `abs(value) < 1e-9` 的项（`service.py:145`），所以只展示真正有贡献的。代价是用户看不到"模型检查过但没用的特征"——这是有意的设计，可解释输出应该是稀疏的。

---

**C6. 讲一个具体的 bug。**

**"非常好吃" 被判为负面。**

根因：否定词检测用的是子串匹配，而 `"非常"` 里含 `"非"`，被误判成否定词，于是"好吃"的极性被翻转。

修法（`sentiment_rules.py:_negation_in_window`）：**先剔除程度副词，再做否定词子串匹配**。

```python
residue = window
for adv in DEGREE_ADVERBS:
    if adv in residue:
        residue = residue.replace(adv, "")
return any(neg in residue for neg in NEGATION_WORDS)
```

并且写了**回归测试**（`tests/test_lexicon.py:100`），锁死"非常好吃必须为正面"。

**这个 bug 想说明什么？** 中文里的规则系统，词表本身也是规则的一部分。程度副词和否定词存在**子串包含关系**（非常 ⊃ 非），这类冲突靠人列词表永远列不完，必须有测试锁住。

### D 组 · Track B / LoRA

---

**D1. 讲一下 LoRA 原理。**

一句话：不改动预训练权重 `W`，在旁边并联一条低秩旁路 `ΔW = (α/r)·B·A`，只训 `A`、`B`。

- `W` 冻结，`W' = W + (α/r)·B·A`
- `A ∈ R^{r×d}`，Kaiming 初始化；`B ∈ R^{d×r}`，**零初始化**——所以训练开始时旁路输出恒为 0，模型行为和原始模型完全一致，不会一上来就破坏预训练能力。
- 推理时可以把 `ΔW` 合并回 `W`，**零额外延迟**。
- 论文的经验：注入到 query 和 value 就够了。

本项目 `r=8, α=16`，所以缩放系数 `α/r = 2.0`。

---

**D2. 296,450 个可训练参数是怎么来的？我能拆开看吗？**

能，我拆过 adapter 的 safetensors 逐层核对过：

```
LoRA 参数：
  12 层 × {query, value} × {A, B} × 6,144
  = 12 × 2 × 2 × 6,144
  = 294,912

分类头：
  Linear(768 → 2) = 768×2 + 2 = 1,538

合计：294,912 + 1,538 = 296,450   ✓ 与报告一致
296,450 / 102,565,636 = 0.289%
```

**一句话总结：分类头只占 1,538 个参数，99.5% 的可训练参数都是 LoRA 本身。**

**追问：分类头结构对吗？我印象里 BERT 是 dense+tanh 两层。**
诚实答：当前产物里存的是**单层 `Linear(768→2)`**，我核对过 safetensors 的 shape。但原版 BERT 的分类头是 `dense(768→768) + tanh + out_proj(768→2)`，约 592k 参数。所以这里和 4.x 的实现有差异，**我没在 transformers 4.x 上交叉验证过**，不确定是 peft 的处理方式还是 transformers 5.x 改了结构。这不影响结论——分类头在两种情况下都是全量训练。

---

**D3. 为什么只 target `query` 和 `value`，不训全部 attention？**

三个理由，按重要性排：

1. **原始 LoRA 论文的结论**就是 query+value 足够，我没必要一上来就加参数；
2. **数据量撑不住更多可训练参数**。11,968 条数据、3 epoch，训练曲线显示 **epoch 1 之后 dev macro-F1 就没再涨**（0.8931 → 0.8902 → 0.8918），而 train loss 一路降到 0.2186——典型的数据不够导致的过拟合。加更多可训练参数只会更早过拟合；
3. **MPS 上训练时间是成本**。全量 attention 会让 285 秒明显变长。

**追问：那 target 全部 attention 会更好吗？**
在数据量不变的前提下，我预计**不会更好，甚至更差**。要验证需要加一组实验，我没做。

---

**D4. 为什么自己写训练循环，不用 `transformers.Trainer`？**

三个理由：

1. **跨版本稳定**。transformers 5.x 与 4.x 的 `TrainingArguments` 字段改名很多（`evaluation_strategy` → `eval_strategy`、`tokenizer` → `processing_class`）。自己写只依赖 `torch`/`peft` 的稳定 API。
2. **可测量**。耗时和内存峰值要按 step 采样，`Trainer` 的回调拿不到 MPS 分配细节。README 里的 285.04s / 0.946GB RSS / 0.386GB MPS 峰值全是实测。
3. **透明**。优化器、LR 调度、梯度裁剪、最佳 checkpoint 选择都能逐行讲清。

具体实现：

```python
optimizer = AdamW(trainable_params, lr=3e-4, weight_decay=0.01)
scheduler = LambdaLR(optimizer, lr_lambda)   # 10% warmup + 线性衰减
torch.nn.utils.clip_grad_norm_(trainable_params, 1.0)

# 逐 epoch 在 dev 上评，按 macro-F1 保留最优权重
if dev_metrics["macro_f1"] > best_f1:
    best_state = adapter_state(model)        # 只拷可训练参数，不拷 390MB
```

**踩过的坑**：`peft` 的 `PeftModelForSequenceClassification.forward` 不会自动传 labels，要显式 `model(**inputs, labels=labels)`，否则 `outputs.loss is None`。

---

**D5. `max_len=64` 怎么定的？会不会截断太多？**

一句话：先量化再定，不是拍脑袋。

实测 token 长度：mean 26.9 / p95 70 / max 458。**`max_len=64` 覆盖 93.72%**，也就是说约 6% 的样本会被截断。

**这是我的已知取舍**：外卖评论里有少数很长的（比如逐条罗列差点的），它们会被截断。我选 64 是因为 p95 就在 70 附近，再往上收益递减而训练时间线性增长。

**追问：那剩下的 6% 怎么办？**
更好的方案是按长度分桶动态 padding（我已经在 collate 里做了 batch 内动态 padding，但没有做长度分桶），或者对超长文本单独走一条分段编码再聚合的路径。两件事我都没做。

### E 组 · 核心结论（这段是全场的重点）

---

**E1. 零样本专用模型 0.9689 比你微调的 LoRA 0.8983 高 7 个点，是不是你的微调失败了？**

一句话：**不是失败，是我这次实验的目的本来就是量化这个边界**。我把这个结论原样写进了 README 的核心章节，没藏。

先说清楚我对比的是什么：

| | 基座 | 预训练是否含情感先验 |
| --- | --- | --- |
| 我微调的 | `hfl/chinese-roberta-wwm-ext` | **否**，只是 MLM 预训练 |
| 对比的 | `Erlangshen-Roberta-110M-Sentiment` | **是**，已在这类中文情感语料上训练过 |

所以 7 个点的差距**不是微调技术的差距，是预训练阶段知识储备的差距**。11,968 条数据、3 个 epoch，补不上预训练阶段已经学到的中文情感先验。

而且我的训练曲线独立印证了这个判断：**epoch 1 之后 dev macro-F1 就没有再涨**（0.8931 → 0.8902 → 0.8918），train loss 却一路降到 0.2186。这说明瓶颈在数据量，不在训练强度——继续训只会更差。

**工程结论**：做情感分类，**先用现成专用模型跑 zero-shot 建基线，再决定要不要微调**。

---

**E2. LoRA 只比 Track A 高 0.34 个点，这算提升吗？**

一句话：**不算。统计上就是噪声，我会明确说"不可区分"。**

Track A test 区间 `[0.8760, 0.9135]`，LoRA test 区间 `[0.8809, 0.9158]`——**几乎完全重叠**。

如果非要给结论：在**同样这份数据、同一个基座**的设定下，把线性模型换成 LoRA 并没有带来可验证的收益。这是个诚实的负面结果。

**我知道该怎么补**：两个模型在同一个 test 集上，应该用 **McNemar 检验**（配对显著性检验），比两个独立置信区间更有统计效率。这是我的方法学缺口。

---

**E3. 那你的 LoRA 不是白做了吗？**

一句话：白做的部分是"提升精度"这个预期；有价值的部分有三块。

1. **证明了链路真的通**。不是"我写了段 LoRA 代码"，而是从数据、分词、注入、训练、dev 选优、存 adapter 到重新加载全跑通，耗时内存全部实测。
2. **量化出了微调的边际收益上限**。"在这台机器、这份数据上，微调的边际收益是 +0.34pp，而零样本先验能带来 +7.06pp"——这个数字本身就是决策依据。
3. **暴露了真问题**。训练曲线告诉我数据不够，这是继续优化的方向，而不是玄学。

**一句话收尾**：我的价值不是"我训了个更强的模型"，而是"**我知道什么时候不该训**"。

---

**E4. 生产环境你会用哪个模型？**

一句话：**我会用 0.9689 那个。Track A 进 API 的理由不是精度。**

诚实讲清楚这个张力：

- **纯看精度和工程成本**：零样本专用模型完胜，7 个点不是小数，而且不需要训练。
- **Track A 进 API 的真实理由**有三个，都不是精度：① 每条预测能给出特征贡献解释；② 零重依赖，冷启动毫秒级，CI 一分钟可复现；③ 19 秒能重训，模型产物不入库也不影响任何人跑起来。

**这是作品集项目的合理取舍，但如果这是真实线上服务，我会换成更强的模型，并且承认解释性会退化。** 我可以退一步的做法是：换更大的专用模型，同时保留一条规则通道做兜底解释。

---

**E5. 如果给你 10 倍数据，你会怎么重做？**

按预期收益排序：

1. **领域自适应预训练（DAPT）**：用无标注的外卖/点评语料继续做 MLM 预训练。这是把"预训练里的情感先验"补到我自己的基座上，比在 12k 条上微调的杠杆大得多。
2. **换更大的基座**（如 6B 级中文模型 + QLoRA）。有了足够数据，LoRA 的容量才不浪费。
3. **更多 LoRA target + 更高 r**，并且这时应该看到 dev 曲线还在涨——现在没涨说明不是容量问题。
4. **阈值按业务代价调**。现在是 `argmax`（等价的 0.5 阈值），真实业务里漏判一条差评和误判一条好评的代价不同，应该在 dev 上按代价优化阈值。

**我不会做的是**：无脑加大数据然后继续调超参刷 test。test 只用一次这条纪律不因为数据变多而放松。

### F 组 · 工程与服务

---

**F1. 为什么模型是懒加载的？health 怎么定义？**

一句话：懒加载让 `/api/health` 能区分"**服务挂了**"和"**模型还没加载**"这两件事。

进程启动不读模型，第一次预测才加载（`threading.Lock` 保证线程安全）。

这里有个真实的坑：**模型是懒加载的，所以冷启动后 `/api/health` 的 `model_ready` 恒为 false**，探针会误报不健康。修法是让 health **主动触发一次懒加载**，并把语义明确定义为"**此刻能否预测**"，而不是"进程里是否已缓存模型"。

```python
@router.get("/health")          # 永远返回 200
def health():
    svc = get_service()
    try:
        svc.ensure_ready()       # 主动触发懒加载
        ready = True
    except ModelNotReadyError:
        ready = False
    return HealthResponse(status="ok", model_ready=ready)
```

`status` 恒为 ok（进程活着），`model_ready` 才表达模型可用。这两个语义必须分开。

**追问：并发下懒加载会不会重复加载？**
不会，`load()` 用 `threading.Lock` 包住，并且内部有 `if self._bundle is not None and not force: return` 的双检。多线程下最多加载一次。

---

**F2. 纯标点输入为什么会返回假置信度？**

因为 `normalize` **保留** `!` `?` `,` `.` 这几个标点——它们是强情感信号，不能丢。但这就导致 `"！！！"` 归一化后**非空**，模型会给出一个无意义的置信度。

修法：新增 `has_content()`，判断归一化后是否还含**汉字/字母/数字**，没有就直接返回 400。

```python
def has_content(normalized: str) -> bool:
    return any(("\u4e00" <= ch <= "\u9fff") or (ch.isascii() and ch.isalnum())
               for ch in normalized)
```

**这个坑想说明什么？** 归一化的目标不只是"清洗"，还有"**保信息**"——不能为了简洁把 `!` 这种高价值信号一起删了。两个目标冲突时，我选择保情感信号，再单独加一道内容检查兜住副作用。

### G 组 · 边界与失效（主动说，别等被问）

---

**G1. 你这个模型在什么情况下会错？**

一句话：**反讽。中文情感分析的老大难，我明确知道它失效，没有解决它。**

Demo 里内置了这条真实样本：

> 「菜品质量好，味道好，就是百度的问题，总是用运力原因来解释」

词典会命中两个"好"判为正面，人读下来是抱怨。**字符 n-gram 也救不了**——线性模型没有句级推理能力，它看到的是两个高权重 n-gram。

这是**方法论边界，不是 bug**。要解决需要句对关系建模，或者直接标注反讽数据。

**追问：你会怎么改进？**
1. 句对建模（双层结构，先句内编码再做文档级聚合）；
2. 标注反讽样本做专项训练——但反讽标注很贵；
3. 或者靠预训练先验——这正是零样本专用模型赢 7 个点的原因之一，它见过大量这类数据。

---

**G2. 你这个项目明确不做什么？**

主动划边界，我认为这比多做一个功能更能体现工程判断。

- **不做**生产级高并发/鉴权/限流/持久化——这是作品集项目，不是上线服务；
- **不做**模型服务化部署（Docker、量化、ONNX/TensorRT）——推理服务就是本地 FastAPI；
- **不做**深度模型进 API——理由见 E4；
- **不做**中文分词——理由见 B5；
- **不做**数据增强/模型集成/大规模超参搜索——18 组网格是刻意控制的，为了 CI 一分钟复现；
- **不做**反讽专门模块——边界已知；
- **不恢复、不伪造 2022 年毕设的任何细节**。

**G3. 这个项目最大的不足是什么？**

一句话：**dev 集只有 1,197 条，抽样噪声就有几个百分点，这污染了所有基于 dev 的选择。**

具体影响：

- 18 组网格选出的"最优"配置，可能有相当一部分是噪声；
- 消融里 0.001 的差异，在噪声面前完全不可信；
- bootstrap 只做 200 次，分位数估计不稳；
- 该做的 McNemar 配对检验我没做。

**如果重做**：数据扩大到 5–10 万条，用 repeated 5-fold CV（而不是单一 dev 集）做超参选择，bootstrap 提到 1000 次以上，加 McNemar 检验。test 仍然只用一次。

## 5. 5 个刁钻陷阱题

这五个问题都很容易踩，回答的核心是**先承认，再给分析**。

---

**Q1. "你说 0.9689 比你微调的好，是不是你 LoRA 超参没调好？"**

> 有可能，但我有证据说主要不是超参问题。
>
> 最直接的证据是训练曲线：epoch 1 的 dev macro-F1 是 0.8931，epoch 2 掉到 0.8902，epoch 3 是 0.8918。**如果超参有问题，我应该看到 epoch 1 还在涨、后面才过拟合**。实际是第一个 epoch 就到顶然后掉，这是数据量不足的典型形态，不是学习率不对的形态。
>
> 而且超参是在 dev 上选的，dev 有 1,197 条，噪声本身就有几个点。我承认这不足以排除超参因素。
>
> 要真正排除，需要在**更大数据**上重跑 LoRA 并对比零样本——这正是我在 E5 里说的第一优先改进项。

---

**Q2. "你的 LoRA 只训了 0.289% 的参数，这不就是没训吗？"**

> 0.289% 是 LoRA 的正常量级，不是"没训"。
>
> 更重要的是：**分类头是全量训练的**。296,450 里有 1,538 是分类头，294,912 是 LoRA 的 A/B 矩阵。而分类头是**随机初始化**的——微调的主要工作量本来就是在训练这个头，让它对接预训练的表示。
>
> 而且 LoRA 论文的结论就是 0.1%–1% 的可训练参数就够了。全量微调 102M 参数在 12k 条数据上会严重过拟合，那才是真的会"训坏"。

---

**Q3. "MPS 上训练只占 0.386GB，是不是说明 LoRA 特别省显存？"**

> **不是**，我在 README 里专门写了这句话的否定版本，因为这是个常见误解。
>
> 低占用的真实原因有两个：模型本身只有 102M，batch_size 只有 16。这两个参数一变，占用就完全不一样。真实业务里 LoRA 的显存需求随模型规模线性涨，7B 模型 + LoRA 需要的激活显存是另一个量级。
>
> 我给这个数字是为了**可复现和可核对**，不是为了证明"LoRA 省显存"这个结论。那个结论需要拿 7B 模型实测才有意义，我没有那个条件，所以我不下那个结论。

---

**Q4. "0.9689 的模型你直接拿来用了，那你的训练有什么意义？"**

> 意义在**决策规则本身**，不在那个模型。
>
> 我的产出是一条可复用的判断："情感分类任务，先用现成专用模型跑 zero-shot 建基线，再决定要不要微调。" 这个判断不是拍脑袋，是我在自己机器上用同一份 test 划分量化出来的——专用先验值 +7.06pp，LoRA 值 +0.34pp 且不可区分。
>
> 反过来说，如果没有做这个 LoRA，我**没有任何数据**能支撑这条规则，只能说"应该先用现成模型"。做了之后我才能说"我测过，差 7 个点"。
>
> 另外我选的对比模型不是随便挑的——它的 `id2label` 恰好是 `{0: Negative, 1: Positive}`，和数据集语义一致，可以零样本迁移，省掉了"标签映射是否对齐"这个坑。这一点我是在代码里**主动校验**的，不是假设的。

---

**Q5. "你这个 accuracy 0.9064，线上够用吗？"**

> 单独看这个数字**不够**，因为它是 2:1 不均衡数据上的 accuracy。
>
> 我能给的诚实判断是：macro-F1 0.8949，逐类看负面 P/R 是 0.9309/0.9286、正面是 0.8579/0.8622——**正面（少数类）明显更弱**，符合不均衡数据的预期。
>
> 但"够不够用"这个问题我答不了，因为**它取决于业务代价**：漏判一条差评和误判一条好评，哪个更贵？我不知道。所以我现在用的是 `argmax`（等价 0.5 阈值），**这其实是个偷懒的做法**——正确做法应该是在 dev 上按业务代价优化决策阈值。
>
> 而且更根本的是，如果这是线上服务，我会先用 0.9689 那个模型。见 E4。

## 9. 一页纸速记（考前 5 分钟看这个）

```
1. 电梯：双轨。Track A 19 秒 / 0.8949 / 进 API；Track B 285 秒 / 0.8983 / 量化边界。
2. 核心结论：零样本专用模型 0.9689 > LoRA 0.8983（+7.06pp）> Track A 0.8949（+0.34pp，不可区分）。
3. 纪律：超参只看 dev / test 只评一次（写进 JSON，CI 断言）/ 两轨共用同一划分 / 指标只有一份实现。
4. 三个最好的技术故事：
   - "非常好吃"被判负面 → 非常 ⊃ 非 → 先剔程度副词再匹配否定词 + 回归测试
   - 两轨划分对不上 → normalize 改动 → 去重数变 → 必须重跑 Track B
   - dummy accuracy 0.6664 但 macro-F1 0.3999 → accuracy 骗人
5. 主动认的弱点（一定要主动说）：
   - dev 只有 1197 条 → 所有基于 dev 的选择都有噪声
   - bootstrap 只 200 次 → 分位数不稳
   - 该做 McNemar 没做
   - LCG 随机性不如 PCG64
   - max_len=64 截断 6% 长评论
   - 0.289% 可训练参数是 102M 模型的结果，不能推广到 7B
6. 红线（背下来）：
   - 技术范式：BERT 家族**分类**，不是 GPT、不是文本生成。
   - 2022 毕设一个字的具体细节都不说。
   - 没有交叉验证、没有早停 —— 被问就说"没有，我是 dev 选超参 + 跑满回选"。
   - 数字只说 reports/*.json 里有的。
```
